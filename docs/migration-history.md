# マイグレーションの変更経緯

旧 README に記載していた、各マイグレーションの目的と移行時の注意点です。当時の互換性・仕様を含みます。現在の環境構築は [Supabase 環境の構築手順](supabase-setup.md)、最新の更新手順は [リリース前検証](release-readiness.md#既存環境への適用順) を参照してください。

## 2026-10-16 の変更

追加3本で、社員ごとの招待コード、利用停止、最後の利用可能 Admin の保護、評価者変更の Admin 限定、DB による確定集計、通知の重複防止・再送制限を追加しました。以下にある古い「確定値を検算する」処理に加え、現在は DB が確定値そのものを計算します。新規登録には会社メールの認証と社員ごとの招待コードの両方が必要です。

## 以前の変更

受け持ちの評価には `supabase/migrations/202610070001_reviewer_workspace.sql` と `202610080001_evaluation_stages.sql` の適用が必要です。既存の「二次評価者なし」「共通評価項目セット」のマイグレーションを先に適用してください。`202610080001` は `evaluation_sheets.first_rank`（一次評価ランク）と状態 `first_evaluated` を追加し、評価者ごとの確認記録（`sheet_review_checkpoints` と `set_sheet_reviewed`）を削除します。0点を未入力・完了の判定には使いません。一次評価者向けの二次評価・最終結果の非表示、下書きの非表示、一次評価確定の通知先の取得を RPC 側で制御しています。状態の遷移と評価の編集可否は、アプリ側のポリシーに加えて、`202610120001_access_control.sql` から DB 側でも強制しています。

`202610080002_sheet_grade.sql` は `evaluation_sheets.grade_id`（シート作成時の等級）を追加します。等級は挿入時に DB のトリガーが社員の等級から設定し、その後に社員の等級が変わっても書き換えません。評価シート一覧にはこの等級を表示します。PDF を出力できるのは、評価が確定したシートの本人と評価者（一次・二次）です。評価関係のない社員は出力できません。PDF は誰が出力しても同じ内容で、伏せ字にはしません。

`202610080006_reviewer_workspace_sheet_grade.sql` と `202610080007_evaluation_completion_sheet_grade.sql` は、「部下の評価」の一覧と確定時の未評価チェックが使う共通評価の項目を、社員の現在の等級ではなくシート作成時の等級（`evaluation_sheets.grade_id`）に揃えます。昇級後に過去のシートを開いても、作成時の等級の項目のままです。

`202610080008_evaluation_period_management.sql` は、評価期間の管理と期間締めです。Admin が設定画面で評価期間を追加・変更・削除し、「この期間を開始する」で次の期間を実施中にすると、それまで実施中だった期間が同時に締められます（DB 関数 `activate_evaluation_period`）。実施中の期間は常に 1 つで、`is_active` はクライアントから直接は書き換えられません。締める期間に未確定の評価シートが残っていると締められません。締めた期間の評価シート・チャレンジ目標・共通評価の結果は、DB のトリガーが追加・更新・削除を拒否します（閲覧と PDF 出力はできます）。間違えて締めた場合は、元の期間をもう一度開始すれば戻せます。適用時に実施中の期間が複数あるとマイグレーションが失敗するので、先に 1 つにしてください。締めた期間のシートを後からマイグレーションで書き換える場合は、そのマイグレーションの中でトリガーを一時的に無効にする必要があります。

`202610080009_sheet_evaluators.sql` は、評価シートに評価者（`primary_evaluator_id`、`secondary_evaluator_id`、`no_secondary_evaluator`）を持たせます。シートの作成時に社員マスタの評価者が入り、未確定の間は社員マスタでの付け替えが反映されます。評価が確定したシートの評価者は変わらないので、次の期間に向けて評価者を付け替えても、過去のシートは評価した人のまま閲覧・PDF 出力できます。既存のシートには、適用時点の社員マスタの評価者が入ります。`202610080008` の後に適用してください。

`202610080010_notifications_by_sheet_evaluators.sql` は、通知先の取得（一次評価の確定・評価の確定）と確定時の未評価チェックを、社員マスタではなくシートの評価者で判定するように直します。`202610080011_unique_rows.sql` は、評価期間・社員ごとに 1 シート、シート・目標番号ごとに 1 目標、シート・項目ごとに 1 結果の一意制約を揃えます（本番に既にあるものはそのまま、`milestones` の分を追加）。`milestones` に同じシート・同じ目標番号の行が重複していると失敗するので、その場合は先に重複を解消してください。目標の保存はこの制約を使うため、アプリの配布前に適用が必要です。

`202610080013_workspace_settings.sql` は、ワークスペース全体の設定（`workspace_settings`、常に1行）を追加します。会社のメールドメイン（旧 `VITE_REQUIRED_DOMAIN`）と、通知メールの SMTP 設定（旧 `VITE_SMTP_*`）をここに持ちます。ログイン画面がこのマイグレーションの DB 関数で会社ドメインを読むため、**アプリの配布前に適用が必要です**。会社ドメインは、登録済みアカウントの内部用アドレスから自動で入ります。SMTP 設定は空で始まるので、適用後に Admin が設定画面の「通知メール」で登録してください（登録するまで通知メールは送れず、確定のたびにエラーのトーストが出ます）。アカウントが1件もない環境では、`update public.workspace_settings set required_domain = 'example.jp';` を実行してください。

`202610120001`〜`202610120010` は、アクセス制御を DB 側へ移すマイグレーションです。**適用の順番を守ってください**（[基本設計書 13.3](basic-design.md#133-アクセス制御のマイグレーションを当てる順番)）。

- `202610120001_access_control.sql`: 行レベルセキュリティと列権限・トリガーで、「誰が・どの段階で・どの項目を」読み書きできるかを DB が決めます。ログイン前（anon）は会社ドメインの取得だけ、社員は自分の関係者とシートだけ、という範囲になります。確定時に保存する評価点と評価ランクは、DB が点数から計算し直して一致を確かめます。配布済みの 0.9.8 は、新規登録を除いてそのまま動きます。
- `202610120002_registration.sql`: 新規登録を DB 関数（`begin_registration` / `complete_registration`）に移します。会社のメールアドレスを認証コードで確認したセッションだけが登録を始められ、通知の宛先は `employee_contacts` に DB が控えます。**0.9.8 以前のアプリからは新規登録できなくなります**（ログインと評価は続けられます）。
- `202610120003_sheet_api.sql`: 評価シートを 1 回で読む `get_sheet`、共通評価をまとめて保存する `save_common_evaluation`、通知用の `get_sheet_notification` を追加します。
- `202610120010_after_app_update.sql`: **配布済みのアプリがすべて 0.9.8 より新しくなり、Edge Function `notify-sheet` の送信を確認した後に**適用します。SMTP 設定と通知先を返す DB 関数を削除し、評価の値をテーブルから直接読めなくします。0.9.8 以前のアプリは、これ以降は動きません。

`202610130001_keep_signed_in.sql` は、アプリを閉じた後もログインを残すかどうかを、社員ごとに持たせます（`employees.keep_signed_in`。初めは全員「残さない」）。Admin が社員マスタの「ログイン」で切り替えます。共有 PC を使う社員は「閉じたらログアウト」のままにしてください。この列を読むアプリの配布前に適用します。

`202610220001_import_and_period_terms.sql` は、導入処理と評価期間の運用を広げます。`202610210001` の後に適用してください（`202610160004`〜`202610210001` が当たっていない環境では、先にそれらを順に当てます）。関数はすべて `create or replace` なので、もう一度当てても同じ結果になります。データ取込の画面と期間の分割を含むアプリの配布前に適用します。

- 期と評価期間（`evaluation_periods.term_name` / `division` / `part`）: 評価期間が、どの期（年度）のどの区切り（通年・半期・四半期の何番目か）かを持ちます。期を半期・四半期に分けた評価期間はそれぞれ独立していて、シートを作り、評価し、締める単位のままです（期として点数をまとめたりはしません）。「当期」は、実施中の評価期間と同じ期の評価期間すべてです。既存の評価期間は通年（`full` / 1）になり、期の名前は評価期間の名前と同じです。区切りは作った後には変えられません。期の名前を省いた追加（これまでのアプリ）は、評価期間の名前を期の名前にします（トリガー `fill_evaluation_period_term`）。期の名前は1〜40文字（アプリの決まりと同じ制約を DB にも置き、DB が受け付けた行は必ずアプリが読めるようにしています）。
- 評価期間の状態（`evaluation_periods.closed_at`）: 未開始 → 実施中 → 締め済み の順に進み、戻りません。`activate_evaluation_period` が締めた評価期間に締めた日時を入れ、締めた評価期間をもう一度開始しようとすると拒否します。**これまでの「元の評価期間をもう一度開始して締めを取り消す」はできなくなります。** 実施中と締め済みが同時に立つ行は制約で入りません。適用時、実施中でなく、シートがあるか実施中の評価期間より前に終わった評価期間は締め済みにします。`closed_at` はアプリから書けません。
- データ取込（`get_sheet_import_template` / `import_sheet_data`）: Admin が実施中の評価期間の目標・共通評価・点数を CSV から取り込みます。全行を確かめ、誤りが1件でもあれば何も書かずに、ファイルと行番号つきの誤りをすべて返します。シートは下書きのまま作る・置き換えるので、状態は変わらず通知メールも出ません。提出済み以降のシートがある社員は取り込めません。取込のたびに `security_audit_log` に `sheets.imported` を残します。
- 締めのあいまいさの許容（`evaluation_periods.allow_unfinalized_close`、初めは false）: true の期間は、評価が確定していないシートが残っていても締められます（`activate_evaluation_period`）。正式運用の前の期に目標だけを取り込んで締める、といった使い方です。締めた期間のシートは、下書きのままでも評価者が読めます（`get_sheet`）。アプリは、その期間の確定していないシートの PDF で点数・ランク・評価者のコメントを「***」で伏せます。
- 前の評価期間の目標の引き継ぎ（`milestones.carried_from_id`、`get_previous_goals` / `carry_over_goal`）: シートに、同じ社員の前の評価期間のシートの目標を表示します。前の評価期間は、その評価期間が始まる前に終わった評価期間のうち、いちばん新しいもの（`previous_evaluation_period`。下期なら当期の上期、上期なら前期の下期、間の評価期間が無ければさらに前）で、アプリの `EvaluationCalendar.previousOf` と同じ決め方です。前の評価期間に本人のシートが無ければ、何も表示しません。本人は下書きの間、続ける目標をこの評価期間に引き継げます（チャレンジ目標の文言だけを写す）。引き継がなかった目標は「済み」と表示します。
- 遡及処理（`sheet_corrections`、`get_sheet_for_correction` / `correct_closed_sheet`）: 締めた評価期間を開き直すことはしません。Admin が遡及処理の画面から、締め済みの評価期間のシートの項目（目標の文言・点数、共通評価の点数・一次評価者コメント、総評）を1つずつ直します。直した内容は、修正前後の値・理由・日時・誰が、を `sheet_corrections` に追記し、変更も削除もしません。点数は 1〜4 だけで、二次評価者を置かないシートには二次評価点がありません。評価確定済みのシートは、点数を直すと合計点とランクを確定時の配点で計算し直します（`recalculate_corrected_sheet`）。本人・評価者には `get_sheet` が、直した項目を見られる人にだけ修正を返し、シートと PDF に「締め後修正」として赤字で示します。締めた評価期間への書き込みを止めるトリガー（`require_active_evaluation_period`）は、この関数が同じトランザクションでその1枚を直すときだけ通します。取り消しはできません。

`202610230001_pre_register_employee.sql` は、Admin が導入処理の「初期ユーザ」から社員を仮登録する DB 関数 `pre_register_employee` を追加します（これまでは `employees` に手作業で行を足していました）。権限は Employee で始まり、ログイン用アカウントは本人が招待コードで新規登録するときに作られます。社員番号はログインIDになるため、半角英数字・ハイフン・アンダースコア以外と、既存の番号と大文字・小文字だけが違う番号を拒否します（一意インデックス `employees_employee_no_lower_key`。既に重なっている番号があると適用に失敗するので、先に解消してください）。仮登録は `security_audit_log` に `employee.pre_registered` として残ります。`202610220001` の後、初期ユーザの画面を含むアプリの配布前に適用します。

`202610230002_notification_channel.sql` と `202610230003_in_app_notifications.sql` は、評価の依頼の知らせ方を、アプリ内通知（既定）とメールから選べるようにします。この順で、`202610230001` の後に適用してください。

- 通知の方法（`workspace_settings.notification_channel`）: `in_app` か `email`。`email` は、保存されている SMTP 設定で送信テストに成功した日時（`smtp_verified_at`）があるときだけ選べます（CHECK 制約）。それまでに保存されていた SMTP 設定は、送信テストに成功していないものとして扱うので、適用後はアプリ内通知で動きます。
- SMTP の列（`smtp_host` など）は、クライアントからは書けなくなります。設定画面の「テストメールを送って保存する」で、Edge Function `notify-sheet` が送信テストに成功したときだけ保存します。**この SQL と同時に Edge Function を配置してください。** 古い設定画面（1.0.9 以前）からは、SMTP 設定を保存できなくなります。
- `get_sheet` が通知の方法（`notificationChannel`）を返します。シートの画面は、メールのときだけ「通知メールを送る」と「通知を再送」を出します。
- アプリ内通知（`notifications`）: 状態の変更のトリガー `evaluation_sheets_notify_next_evaluator` が、次に評価する人への依頼を作ります。読めるのも既読にできるのも宛先の本人だけです。

`202610040000_baseline.sql` は、2026-10-07 時点の本番スキーマのダンプです。新しい環境をこのリポジトリだけから作るためのもので、既存の環境には適用しません。

`202610080003_employee_roles.sql` は、Admin が社員マスタから TYPA の権限（Admin / Reviewer / Employee）を変えるための DB 関数 `set_employee_role` を追加します。最後の Admin は外せません。あわせて、クライアントから `employees.role_id` を直接更新する権限を外します（`employees` に列を追加したら、クライアントから更新させる列はこのマイグレーションと同じ形で `grant update` が必要です）。誰がどの権限かは Admin の画面にだけ表示しますが、`role_id` の読み取り自体は、行を読める相手には DB 側で制限していません。

`202610080012_challenge_goal_tabs.sql` はチャレンジ目標を1〜4件に変更し、評価者の一覧でも4件表示します。空欄（空白のみも含む）のある目標は提出・確定をDBでも拒否します。目標タブの追加・削除を使う前に適用してください。
